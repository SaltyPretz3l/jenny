# Desktop Docker command sandbox

Jenny can run foreground commands in a disposable Linux Docker worker while Electron continues to own chat history, approvals, credentials and local inference. This is optional; shell-config v53 migrates existing profiles with the setting off. Enabling requires idle chats and an acknowledged sidecar execution policy. It does not enable hosted mode.

## Setup

1. Install and start Docker independently. Jenny never installs Docker, changes Docker settings or prunes resources. On Windows, Docker Desktop must use its Linux engine with cgroup v2.
2. Open Jenny and configure a tools workspace.
3. Open Settings → Tools → Docker command sandbox and enable it. Turning it on starts in **Synced workspace**; profiles that already had it on keep **Isolated copy**. "Where commands run" switches between the two (row 106; see below).
4. Wait for Ready. Initial preparation builds the application-owned worker image locally from a digest-pinned Linux amd64 base and may download build dependencies. Subsequent commands have no network access. Required emulation must work on non-amd64 hosts.
5. Chat and approve foreground commands normally. Existing current Electron auto/deny policy still applies. Plan/read-only mode prevents command admission.

For source testing, use the repository's normal launch instructions. The sandbox shipped in 1.1; installed-package qualification is still an owner gate (see NEXT_STEPS.md); consult this release's notes before assuming an older installation contains the sandbox.

## Files and commands

This section describes **Isolated copy**; [Synced workspace](#synced-workspace) differs where it says so. Commands always use Linux `/bin/sh`, including on Windows/macOS. `cwd` is a relative Linux path inside the configured workspace copy (default `.`). A command can use installed Python and Node. There is no background option. Maximum duration is 120 seconds and combined output is limited to 256 KiB.

Electron stages a snapshot before approval: at most 64 MiB, 2,048 entries, depth 32 and bounded paths. Links, junctions/reparse points, hardlinks, special files, profile overlap and detected source changes are rejected. Staging files and directories are made read-only, then the content digest and workspace root identity are checked again immediately before admission. The live workspace is never mounted. The worker copies read-only staging into its disposable `/workspace`. **All command-created or edited files are discarded.** Use Jenny's reviewed typed `write_file`/`edit_file` path for durable changes. Large repositories may exceed snapshot limits and must use a suitably bounded workspace. A refused snapshot (too large, a link or special file, a concurrent change) fails only that command and leaves the sandbox Ready; the model is told the limits and that retrying fails the same way, and a command card's Run says why nothing ran.

The worker has no network, profile, credentials or Docker socket; root filesystem is read-only. Jobs run as UID/GID 10001 without effective capabilities. The trusted PID-1 supervisor keeps only SETUID/SETGID and enforces seccomp/no-new-privileges plus Docker's private namespaces, 2 CPUs, 2 GiB with no swap, 128 PIDs, 512 MiB workspace and 64 MiB temporary storage. A container incarnation accepts one job. Its successor authenticates the terminal result; Docker's changed startup identity confirms namespace replacement before cleanup is reported. Each desktop container serves one run and is removed after its successor reports, so the worker reports ready as soon as it has started (`main(ready_delay=0.0)`); the hosted long-lived worker keeps its 10 s readiness delay, which only keeps Docker's restart backoff from growing across back-to-back jobs. Cleanup never relied on it: PID 1's exit reaps its whole namespace.

## Synced workspace

A synced-workspace command runs offline in a Linux volume that mirrors the workspace. It never sees the folder itself, the profile, credentials or other folders. After it ends, Jenny copies back the regular files it added, changed or deleted, except the protected set, links, special files and files you changed meanwhile, after taking a restore point when one is possible. Every applied change is listed, and the model is told which paths were not copied back. Commands can still change files that run later on this computer (package.json scripts, Makefiles, `.vscode/tasks.json` or `settings.json`, `.envrc`, `.pre-commit-config.yaml`): the Changed-files row flags them.

- **Mirror.** One Docker named volume per workspace (`jenny-mirror-<owner>-<id>`, owner-labelled). Each run stages only the delta since the last write-back into the read-only staging mount; the worker applies it as UID 10001 before the job and records what the mirror held. Limits: 4 GiB, 200,000 entries, depth 64. Links, junctions and special files in the folder are skipped (not copied in, never written back); hardlinked files sync by content. The mirror's index is trusted only between runs: it is dropped when a command is admitted and rewritten after write-back, so a crash forces a full resync. Copy mode keeps no mirrors; Synced mode keeps the four most recent for 30 days. The mirror volume has no Docker size quota, so a command can fill the Docker VM's disk.
- **After the job.** The successor worker incarnation compares the mirror with the recorded state and writes a bounded outbox (256 MiB, 10,000 entries) that only a helper group can reach; the job's user cannot. The host write-back is the only writer of the folder, and only after container cleanup is confirmed.
- **Never written back:** `.git`, `.jenny`, the folder `core.hooksPath` names (read from the repository, worktree, global and included Git config, so a linked worktree's shared config counts), `.husky`, any file named `HEAD` (it would turn a folder with `objects/` and `refs/` into a repository Git honours), submodule gitfiles/gitdirs, in-root Git config includes, `node_modules`, `.venv` and `venv` at any depth, matched the way NTFS compares names (case, trailing dots/spaces). Names Windows reserves or shortens (`CON`, `NUL.txt`, `GIT~1`, trailing dot or space) are refused. A parent that is a junction or link is refused. `.git`, `.jenny`, `.venv`, `venv` and gitdirs are not synced into the mirror at all.
- **Conflicts.** A file whose size, time, identity or SHA-256 changed since sync-in is not overwritten; it is listed as a conflict and resynced next run. Write-back holds no workspace lease, so this check is the guard for edits made during the run.
- **Restore point and Undo.** After approval and before the command starts, Jenny pins a Git checkpoint under `refs/jenny/sandbox/<chat>/<n>` (20 per chat, 100 total, 30 days, separate from turn checkpoints). Without one (not a Git repository, a repository subfolder, no commit yet, untracked files over the checkpoint caps) the card always asks and says there is no undo, even where Auto would run; a checkpoint that fails refuses the run. Undo restores per file (up to 500) in the chat's project root. The checkpoint holds tracked files and untracked files Git does not ignore, so a written-back change to an ignored file (build output, `.env`) or a file inside a submodule has no undo, and the Changed-files row offers Undo only for the first 20 diffs; the whole pre-run state stays reachable with `git restore --source=<ref> -- .` until the checkpoint expires. Restore content round-trips raw: an unmodified Git LFS or clean/smudge-filtered file is restored as its stored bytes.
- **Approval.** Auto policy and chat auto-run apply only with a restore point and only after you approved that grant once in Synced mode. Read-only commands are unaffected.
- **Kill switch.** `JENNY_ENABLE_SANDBOX_SYNCED_MODE=0` forces Isolated copy and hides the choice. The hosted (Docker browser) bridge always uses the disposable copy.

## Unsupported execution

Only foreground `run_command` is qualified. Temporary scripts, `python_execute`, background commands/monitors, Git subprocess tools, verification runners, LSP, third-party MCP, executable plugin tools, delegation, automatic turn checkpoints/worktrees and provider-owned execution integrations are unavailable. The one host Git use is Synced workspace's own restore point, which runs every Git verb neutralized (no repository hook, filter, fsmonitor or credential program runs) and never enables the model's Git tools. Reviewed typed file tools and ordinary user-operated desktop controls remain separate. The read-only chat directory (`sessions_list`, `session_status`, `session_transcript`) stays available so the primary Jenny chat can still see other chats; its other tools (messaging, settings, schedules, conversation search, exports, terminal) are unavailable, and its prompt overlay says so. While the sandbox is not Ready, a command card offers Copy only. Local managed model inference is unchanged. A command cannot fall back to host execution when Docker fails or the setting is disabled.

## State and recovery

Disabled means the optional backend is off. Preparing includes image build and a real worker contract check. Ready admits one transaction. Busy includes snapshot preparation, approval and execution; competing conversations get a bounded refusal and are not queued. Workspace changes before admission invalidate approval and cancel admitted work; in Synced workspace a file you change while the command runs is not overwritten (a conflict). Settings, including the mode, cannot change during a transaction or an active chat; a command card proposed under the other mode offers Copy only until the mode matches again.

Unavailable reports a prerequisite/preparation failure. Start Docker with the Linux engine and select a local Docker context, then Retry. Remote TCP/SSH Docker endpoints are rejected. Recovery required means Jenny cannot prove cleanup; new execution stays blocked. Retry inspects only resources with this profile's deterministic Jenny ownership labels, stops/removes their namespaces and reconciles pending receipts without replaying commands. Restoring Docker access may be necessary. Do not treat killing a CLI or shell as cleanup proof.

Admission is flushed to a bounded profile journal before submission. Bounded terminal results are flushed before pending state clears. Startup discovers owned containers even with missing receipts; torn data is preserved for diagnosis and reconciled only after namespace cleanup. Unresolved receipts are not compacted away. Shutdown stops only this profile's Jenny resources. Prepared images and the protected control volume may remain for reuse; Jenny performs no broad cleanup.

## Qualification

On 2026-09-09 the real Windows Docker Desktop Linux amd64 daemon (Engine 29.7.2, cgroup v2) built and ran the packaged allowlisted worker context. Confirmed: UID/GID 10001; host workspace unchanged; external network and controller-key access denied; no daemon socket; timeout; cancellation; 256 KiB output truncation; detached-descendant namespace cleanup; temporary storage exhaustion; PID exhaustion at 124 child processes; memory termination (exit 137); authenticated successor results and owned-container removal; profile service restart; actual controller termination during admission followed by startup recovery with intact, missing and torn Windows journals (no replay). The reproducible probe is `node scripts/packaging/probe-desktop-command-worker.js`; `--recovery` exercises controller termination and intact/missing/torn receipts with disposable profiles. `--wire` exercised the actual Docker stdin relay: malformed frames, forged authentication, trailing data, idempotent duplicate submission (one execution), competing jobs, stale incarnation rejection and exact Windows staging-mount identity. `--smoke` repeats the isolation case. `--synced` (row 106) runs the Synced workspace round trip on a disposable Git workspace: edit, create and delete written back, the restore point pinned, `.GIT/config`, a symlink, `NUL.txt` and `node_modules` refused, a file edited during the run kept as a conflict, and a no-op run's delta timing. It has not yet been run against a real Docker daemon (owner gate). Windows journal tests also cover repeated corruption with bounded diagnostic archive rotation.

An owner-authorized Windows computer-use pass also drove the actual Electron Settings and chat UI with deterministic replay commands: enabling to Ready, Allow once with real Docker output, Deny with no admission, Stop with confirmed cleanup and a Cancelled tool card, and full app close/relaunch preserving successful and cancelled Docker result metadata. The pass found and fixed private-attribution argument forwarding and cancellation-result persistence.

On 2026-11-03 the same Windows Docker Desktop daemon (Engine 29.9.2) ran `node scripts/packaging/probe-desktop-command-worker.js --synced` on a disposable Git workspace: an edit, a create, a delete and a new subfolder came back with a restore point pinned each run; `.GIT/config`, `node_modules`, a symlink and `NUL.txt` were refused and `.git/config` stayed byte-identical; a host edit made mid-run was kept and listed as a conflict; a no-op delta ran clean. Each run took about 24 s in both modes, set mostly by the worker's 10 s readiness delay, paid by the first incarnation and again by its successor; desktop containers have dropped that delay since (see above), and the same probe re-run then took about 4.3 s per run with every case passing.

Linux and macOS adapters are implemented but not live-qualified. Unit/fake tests do not qualify a host platform. The complete GUI smoke suite, full CI, packaged installer launch and a machine-wide Docker daemon stop/restart remain outstanding owner/environment gates. The test suite simulates Docker loss without disrupting other Docker workloads.
